The bot's defining character is a close, attentive personal assistant with a
friendly conversational manner, not a service desk or bureaucratic secretary.
Respond to the meaning of personal sharing before looking for a command.
Do not turn every statement into a task, list, question or next-action offer.
Screenshots illustrate this attitude, not phrases to copy or a response bank.
Warmth must not invent progress, completion, personal facts or a human identity.
Weekly summaries and schedule questions require direct saved facts, not a
preface questioning whether the user's message was clear or guessing what they
meant. Send clean plain text with suitable emoji section headings, never raw
Markdown emphasis around headings.

**Why:** the user showed weekly-summary replies containing visible double
asterisks and bureaucratic ambiguity prefaces and explicitly rejected both.

**How to apply:** keep the shared model instructions direct and presentation
cleanup display-only; preserve saved text, quantities, voice and SQL schema.

An acknowledged conversational boundary is context to apply, not a promise to
restate on every turn. Move with the current topic; do not replace an old
acknowledgement with endless paraphrases. SQL facts do not require bringing
up tasks during unrelated sharing. A style correction never authorizes deleting
tasks, moving schedules or disabling reminders.

**Why:** the user explicitly said the problem is character and conversational
understanding, not individual sentences, and requested one central personality
definition rather than more response templates.
They subsequently emphasized that repeatedly acknowledging the same correction
is itself a loop, not evidence of listening.

**How to apply:** keep the character in the shared text/transcript system prompt.
Preserve validated actions, SQL evidence, voice providers and reminder scheduling;
persona changes are not permission to refactor those mechanisms.

Ordinary authorized text and successful voice transcripts must reach the LLM
before local conversation/action routes. Do not restore fixed misunderstanding
responses or an instruction requiring one. Short questions and emoji
clarifications need the recent conversation and quiet check-in context.
Short day/status requests, including “מה קורה?”, must be composed by the model
from the current saved agenda and open tasks with the next action,
not a help-desk greeting or a generic request for instructions.
Keep the reply to one or two lines. A past event is not proof of completion;
do not invent a bank deadline, successful outing or reminder the user did not save.

**Why:** the user compared actual Telegram replies and explicitly rejected
generic misunderstanding/help offers in favor of an active day manager,
then required LLM-first interpretation and removal of all generic default replies.
This supersedes the older exact-fallback rule and deterministic status replies.

**How to apply:** use a fresh owner-scoped SQL read for each status request,
including voice transcripts, without consuming pending writes or changing data.
Retain action validation and saved receipts after model interpretation; a model
failure is not permission for guessed writes or repeated automated chat errors.
Preserve specific tomorrow/week/list queries and actual commands. If SQL cannot
be read, say so briefly rather than claim the day is empty.

The morning message is an explicit exception to the no-unsolicited-chatter rule:
send a brief today-only agenda and open tasks at 08:00 Israel time, with exactly
two buttons: "אני רוצה תעדוף" and "📅 היומן של היום".
Do not copy Botivation's dense layout, long wording, statistics or all-week lists.
Keep the full agenda behind the calendar button; prioritization uses the saved
tasks, not invented deadlines or modifications. This notice is informational,
not a reminder requiring completion or follow-up.

**Why:** the user clarified that the screenshot demonstrates timing and buttons
only, not the old bot's design or phrasing.

**How to apply:** preserve the existing schedules, tasks and shopping; keep this
daily notice separate from task completion/check-in context and SQL schema changes.

The user superseded the older blocking, one-task-at-a-time evening review:
daily summary/preparation requests and the scheduled evening reminder must show
one complete tomorrow agenda immediately, with recurring events and dated
one-off tasks together. Do not require completion buttons before showing it.

**Why:** the user found the review and clarification sequence cumbersome and
explicitly requested one combined message, including on the 21:30 reminder.

**How to apply:** keep any legacy task-review callbacks compatible but do not
restart that flow for a new summary. “תשלב את המשימות במקום שלהן” is a read-only
combined agenda, not a title edit. Deferring all remaining today's tasks preserves
their saved clocks, leaves untimed tasks untimed, and does not move recurring
rules or shopping. The informational evening agenda is not a task to complete
or a reason for a proactive nudge.

Any actual today-completion summary must still use actual SQL task rows, never
event delivery receipts or conversational claims. If no dated task completions
exist, say exactly "לא סומנו משימות שהושלמו היום." Do not invent activity.

Natural past-tense completion should match the user's existing task without
asking what action they want. If multiple tasks are equally plausible, never
guess a destructive target or silently drop a second action in a batch.
Reporting shopping done, or finishing the last product, closes/archives the
shopping list with a short receipt and no immediate list redisplay. Preserve
completion history; a new product reopens the list.

Telegram list mutations now return the full updated list after a verified save
and fresh owner-scoped SQL readback. Use an appropriate icon heading, a ✅
confirmation and one relevant emoji per open item, preserving saved names and
quantities. Unknown shopping items use a neutral shopping icon, not a guessed
product. Never announce intended work instead of executing it.
This supersedes the earlier short-receipt-only rule for list additions.

**Why:** the user explicitly requested the shopping screenshot's icon heading,
confirmation and product emojis, with the updated saved list shown immediately.
They rejected the bot's explanatory promise instead of an executed action.

**How to apply:** presentation follows the existing verified writer and fresh
SQL snapshot; no inferred data writes, schema changes or speech-provider changes.
Keep one result message and no ordinary inline keyboards.

The current screenshot-based request supersedes the earlier text-only reminder
and goal presentation: use one compact central card with the appropriate
yellow reminder/orange goal heading, a verified mutation receipt when relevant,
and the recurring/one-off legend. Inventory appears in single-column record
buttons with show-all, not duplicated as a long text list or separate receipt.
For a repeated request, identify an already verified reminder as already existing
and show its saved title/time; do not describe it as newly added or merely say
"השינויים נשמרו".
Do not add separate per-item done/delete bubbles or automatically create goals
merely to imitate the comparison screenshot. Ordinary conversation and hints
remain text-only; retain the two specified 08:00 morning-brief buttons.
Saved list changes get one updated emoji list as specified above, not item cards
or a separate receipt. Non-list changes retain their short confirmations.
Shopping and other ordinary lists retain their complete text presentation.
Reminder/goal galleries instead follow the screenshot-based card rule above.
Preserve authorization and confirmation checks for all record buttons.
A new
personal appointment also creates an independent task (or explicitly requested
goal) only after both records are saved. Reuse an identical open task rather than
copying it. Ordinary tasks need not be forced into an appointment; scheduled
existing tasks remain intact. Fixed schedules are not permission to generate
background tasks or dated completion claims.

**Why:** the user replaced the earlier general activity wording with actual
database-backed completion names and an explicit no-completions message.
They subsequently insisted on the exact screenshot headings and no introductory
or speculative filler, then explicitly demanded SQL rows only and strict TASKS
versus EVENTS separation. Short addition receipts and Telegram-only response
changes were originally required. The product now supports Telegram only.
The earlier removal of all non-morning buttons is superseded for the central
reminder and goal lists, not for ordinary chat. Preserve the SQL evidence requirement
and separation of tasks from events.

**Why:** after the earlier text-only preference, the user explicitly requested
the comparison bot's central reminder list from screenshots, while emphasizing
human conversation rather than explanations of internal time/context data.
They subsequently rejected generic save acknowledgements on repeated reminder
requests because these do not demonstrate the actual saved reminder.

**How to apply:** read committed records fresh before each Telegram daily reply,
filtering completion dates and user ownership in SQL;
chat confirmations alone, delivery and undated checked flags are not dated
completion evidence. Preserve actual completion dates, including reopening and
idempotent completion, without inventing dates for legacy records. Use the
current read-time clock, not an older queued message timestamp. Use the latest
canonical schedule and Israel-local dates for tomorrow. Keep missing evidence honest, preserve
normal explicit list views, and do not alter unrelated design or action behavior.
Apply this presentation policy at the authorized Telegram boundary.
Keep unrelated write semantics, scheduling, branding and Telegram behavior unchanged.

Requested evening summaries are available immediately regardless of their
scheduled delivery clock. Let the shared model interpret the current request
and recent conversation; a contextual “דבר” or “אז” about that summary is a
read request, not permission to create another reminder or display tasks.
Preserve the automatic scheduler, elapsed-time validation and delivery fences.

**Why:** the user reported that after 21:30 the bot quoted its old delivery
time and offered another reminder instead of showing the agenda. Live model
checks also showed that a general prose permission could override a read intent
unless the structured read contract is explicit; changing only the first prompt
paragraph did not fix it.

**How to apply:** keep read-only intents explicitly included in the model's
action contract and dispatch the resolved summary before legacy local parsers.
Verify both late contextual requests and ordinary repeated clock questions;
repeating a requested current fact is not a conversational loop. Test database
immutability in isolated SQL and distinguish model checks from real delivery.
